# Wave 9 Compliance/Audit Attestation

IX-BlackFox Wave 9 adds a compliance/audit attestation layer for AI-assisted code-change governance.

The purpose is not to claim certification. The purpose is to make the review boundary inspectable:

```
policy pack
  -> evidence manifest
  -> control evaluation
  -> reviewer signoff validation
  -> deterministic governance report
  -> human decision
```
The governing rule remains:
```
AI proposes. Humans decide.
```
Wave 9 treats model output as untrusted input. It does not let a model, system process, generated report, or CI job approve its own authority.

Audit report flow

Wave 9 governance reporting follows this flow:
```
AuditSubject
  -> AuditEvidenceManifest
  -> EvidenceManifestValidationResult
  -> AuditPolicyPack
  -> AuditControlEvaluation
  -> SignoffValidationResult
  -> SignoffAuthoritySummary
  -> Wave9GovernanceReport
```
A generated report can have one of three dispositions:
| Disposition   | Meaning                                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| `audit_ready` | Required controls passed and required human authority is bound to the current subject and policy pack.   |
| `warning`     | The report is structurally valid, but advisory warnings remain.                                          |
| `blocked`     | Required evidence, validation, policy, provenance, or human-authority conditions are missing or invalid. |
A blocked report is still useful. It explains why audit readiness was not reached.

Default controls

The default Wave 9 policy pack includes these control IDs:
| Control     | Purpose                                                                              |
| ----------- | ------------------------------------------------------------------------------------ |
| `BF-W9-001` | Model output is untrusted input.                                                     |
| `BF-W9-002` | Policy pack identity and digest are bound to the audit.                              |
| `BF-W9-003` | Evidence manifest uses deterministic artifact metadata.                              |
| `BF-W9-004` | Wave 5 PR/workflow evidence is present when change-review scope requires it.         |
| `BF-W9-005` | CI evidence is bound to the reviewed head SHA.                                       |
| `BF-W9-006` | Wave 6 sandbox evidence is present when sandbox claims are made.                     |
| `BF-W9-007` | Wave 7 model-repair evidence is present when model routing or repair is claimed.     |
| `BF-W9-008` | Wave 8 repository-intelligence evidence is present when repo-impact claims are made. |
| `BF-W9-009` | Missing, malformed, zero-byte, or mismatched evidence blocks audit readiness.        |
| `BF-W9-010` | Unverified provenance or attestation claims are not accepted as verified evidence.   |
| `BF-W9-011` | Human signoff is required for audit-ready disposition.                               |
| `BF-W9-012` | Model or system self-approval cannot satisfy authority.                              |
| `BF-W9-013` | Explicit non-claims are preserved in every governance report.                        |
| `BF-W9-014` | Required evidence gaps block audit readiness by default.                             |
| `BF-W9-015` | Governance report is deterministic and digest-bound.                                 |
Evidence standards

Wave 9 evidence artifacts must include:

stable artifact ID
evidence kind
source wave
repository-relative path
SHA-256 digest
positive byte size
producer
head SHA when generated by an internal IX-BlackFox wave
schema version when available
verified/unverified boundary
metadata

Wave 9 rejects or blocks on evidence that is missing, malformed, empty, undigested, head-SHA mismatched, or outside the repository root.

Human signoff boundary

Wave 9 signoff validation uses digest binding.

A signoff is authoritative only when it is:

a human reviewer signoff
an approval decision
bound to the current audit subject digest
bound to the current policy-pack digest

Model and system signoffs are allowed as advisory records. They do not satisfy human authority.

This is intentional. IX-BlackFox does not allow model self-approval.

CLI commands

Generate a Wave 9 governance report:
```
blackfox audit report \
  --root . \
  --repository IX-BlackFox \
  --head-sha local \
  --scope "repository intelligence audit" \
  --claim "repository intelligence impact architecture_memory" \
  --output .blackfox-artifacts/wave9/wave9-compliance-audit-report.json
```
Validate a report shape and digest:
```
blackfox audit validate \
  --report .blackfox-artifacts/wave9/wave9-compliance-audit-report.json
```
Gate on audit readiness:
```
blackfox audit gate \
  --report .blackfox-artifacts/wave9/wave9-compliance-audit-report.json
```
Generate CI evidence:
```
python scripts/run_wave9_compliance_audit_ci.py --head-sha local
```

Why the default CI report is blocked

The default GitHub Actions workflow intentionally expects a blocked disposition.

That is correct behavior.

CI can prove the audit engine generated a valid report, but CI must not fabricate a human reviewer. A valid blocked report proves the engine, policy pack, evidence manifest, control evaluation, report digest, and human-approval boundary are working without pretending that audit approval exists.

The workflow validates the report shape and digest, then uploads the Wave 9 evidence artifacts.

Standards alignment boundaries

Wave 9 includes bounded mapping notes to public assurance and DevSecOps concepts such as evidence manifests, assessment-result-style reports, provenance discipline, attestation verification boundaries, and CI/CD metadata.

These mappings are alignment references only.

Wave 9 does not claim formal compliance with OSCAL, NIST SSDF, SLSA, in-toto, Sigstore, GitHub artifact attestations, RMF, ATO, cATO, DoD Enterprise DevSecOps, or any procurement framework.

Non-claims

Wave 9 audit attestation does not certify correctness.

Wave 9 audit attestation does not replace human review.

Wave 9 audit attestation does not mean the repository is production-ready.

Wave 9 audit attestation does not mean the code is formally verified.

Wave 9 audit attestation does not mean the code is certified.

Wave 9 audit attestation does not mean the code is approved by any government or defense organization.

Wave 9 audit attestation does not grant ATO, cATO, procurement approval, deployment authority, operational authority, or release authority.

Wave 9 audit attestation does not prove DoD endorsement, affiliation, acceptance, or certification.

Wave 9 audit attestation does not make AI coding autonomous.

Wave 9 audit attestation does not authorize autonomous code changes or autonomous release decisions.

Wave 9 audit attestation does not treat model confidence as evidence.

Wave 9 audit attestation does not allow model or system self-approval to satisfy human authority.

Wave 9 audit attestation does not treat recorded provenance metadata as verified provenance unless verification evidence is actually present.

Positioning language

Avoid wording like:

“Wave 9 makes IX-BlackFox compliant.”
“Wave 9 makes the repo DoD-ready.”
“Wave 9 proves patches are safe.”
“Wave 9 provides ATO or cATO evidence automatically.”
“Wave 9 lets AI approve code changes.”
“Wave 9 verifies Sigstore/SLSA provenance by default.”

The correct positioning is:

Wave 9 makes AI-assisted code-change governance more auditable by binding policy packs, evidence manifests, control results, reviewer signoff, non-claims, and deterministic governance reports into one inspectable audit-attestation layer.

Wave 9 is source-available research implementation, not operational certification.
